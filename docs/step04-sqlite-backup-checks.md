# Шаг 04 — закрытие SQLite-соединений перед переименованием снимка

Причина ошибки WinError 32: контекст sqlite3.Connection управляет транзакцией,
но не закрывает соединение. В шаге 03 оба соединения оставались открытыми
при попытке переименовать .sqlite3.partial. На Linux переименование открытого
файла допустимо, поэтому прежняя проверка не обнаружила дефект.

Исправлено: contextlib.closing явно закрывает оба соединения до проверки размера,
переименования и очистки временного файла. Закрытие гарантируется при ошибке
создания назначения и при ошибке копирования. Ошибка удаления .partial логируется
и больше не подменяет исходную ошибку резервного копирования.
В прежнем тесте SQLite также закрыты соединения для работы на Windows.

Автоматически проверено на Linux / Python 3.12 / Django 5.2.8:
- 13 тестов (9 прежних + 4 регрессионных) — OK;
- проверка закрытых дескрипторов непосредственно перед Path.replace;
- закрытие исходника, если соединение назначения не открылось;
- закрытие обоих соединений до очистки после ошибки копирования;
- сохранение причины ошибки при отдельном отказе удаления временного файла;
- регрессионный тест падает на исходном коде шага 03 и проходит на исправленном;
- файловая тестовая SQLite: проверенный снимок создан, 6 категорий добавлены;
- повторная проверка: create=0, skip=6, conflicts=0;
- установка и откат патча на отдельной копии, точное восстановление байтов,
  отказ при пользовательских изменениях, совместимость CRLF/LF;
- Django system check — no issues.
Вживую на Windows и production проверка не выполнялась; ограничение Windows
воспроизведено проверкой состояния реальных SQLite-соединений до файловой операции.
Вёрстка и браузерные сценарии не менялись, браузерные проверки не требуются.

Патч не изменяет пользовательскую БД, не удаляет старые .partial и не содержит
миграций. После установки повторите prepare_furniture_categories --apply:
команда создаст новый проверенный снимок в patch-backups перед записью.
Префикс снимка останется step03-before-furniture-categories, поскольку это повторное
применение данных шага 03 после исправления кода шагом 04.
